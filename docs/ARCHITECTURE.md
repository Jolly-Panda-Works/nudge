# Architecture

## Layers
```
Android (Kotlin)                          Flutter / Dart
┌──────────────────────────────┐          ┌─────────────────────────────────────────┐
│ NotificationCaptureService   │          │ platform/   CapturePlatform, exporter    │
│   posted / removed / snapshot│          │ application CaptureIngestor              │
│        │ append               │  wake    │ domain/     mapper, ingest policy, models │
│        ▼                      │ ───────▶ │ data/       Drift DB + repositories       │
│ CaptureQueue (JSON lines)     │ ◀─────── │ ui/         inbox, details, settings      │
│ ContentIntentRegistry (memory)│ peek/ack └─────────────────────────────────────────┘
└──────────────────────────────┘
```
- `lib/domain/` is pure Dart with no Flutter or database imports: models, `NotificationMapper`, `decideIngest`/`CapturePolicy` and the repository interfaces.
- `lib/data/` implements the interfaces with Drift (SQLite). Timestamps are stored as UTC epoch milliseconds.
- `lib/platform/` hides the Android channels behind `CapturePlatform`, so everything above it is testable without a device. Non-Android platforms use a no-op implementation.
- `lib/application/` contains `CaptureIngestor` (native queue to database), `TextImporter` (shared or pasted text), `RetentionService` (age-based deletion) and `CaptureStatusController` (access and listener state for the UI).
- `lib/ui/` holds the screens: inbox (live stream from the repository), notification details, settings and the app filter screen. Screens depend only on the interfaces through `AppServices`, so widget tests use in-memory fakes.
- Kotlin code lives in `android/app/src/main/kotlin/app/nudge/capture/`. The generated `MainActivity.kt` and `AndroidManifest.xml` are patched by `tools/wire_capture.py` (run through the **Wire Android capture service** workflow), because the `android/` project is generated by `flutter create`.

## Capture pipeline
1. `NotificationCaptureService` receives `onNotificationPosted`, `onNotificationRemoved` and, after `onListenerConnected`, the list of active notifications.
2. Each event is appended to `CaptureQueue`, a small JSON-lines file in the no-backup directory with a sequence number per event. `PendingIntent`s go only to the in-memory `ContentIntentRegistry` and are never serialized.
3. The service sends a wake signal on the event channel. The signal carries no data, so no notification content passes through it.
4. `CaptureIngestor` calls `peek`, applies each event, then `ack`s up to the last sequence number. Events are acknowledged only after they were stored, so a failure leaves them queued and the next drain retries.
5. For a posted event, `RawNotificationPayload.fromMap` validates the map, `NotificationMapper` trims text, detects redacted content and computes a content hash, and `decideIngest` returns `insert`, `update`, `ignoreDuplicate` or `ignoreFiltered`:
   - filtered by the capture policy (allowlist/blocklist, own app, ongoing, group summaries);
   - same key and same content is a duplicate;
   - same key with changed content is an update; a removed entry that reappears is reactivated;
   - readable content is never overwritten by a redacted version;
   - identical content under a new key within a short window is a duplicate re-post.
6. `DriftNotificationRepository.ingest` runs lookup, decision and write in one transaction.
7. A removal marks the entry as removed but keeps its content, so tasks created from it stay valid. A snapshot event reconciles stored state: `markRemovedExcept(activeKeys)`.

## Import, export and deletion
- **Import:** `ShareReceiver` (called from `MainActivity` for `ACTION_SEND` with `text/*`) appends a `shared` event to the same native queue, so it is stored by the ingestor. The in-app "Import text" button calls `TextImporter` directly. Imported entries use the synthetic package `app.nudge.shared` and bypass the capture filters, because the user chose them.
- **Export:** `exportNotificationsJson` serializes every stored notification. On Android `DocumentExporter` opens the system file picker (Storage Access Framework), so no storage permission is needed; on desktop `FileDataExporter` writes to a `Nudge` folder in the documents directory. The file contains full text and is not encrypted; the UI says so before exporting.
- **Deletion:** one notification (`deleteByKey`) or all (`deleteAll`, plus `clearQueue` for events still waiting in the native queue).
- **Retention:** `RetentionService.apply` deletes entries not updated for the configured number of days. It runs at startup and when the setting changes.
- **Logging guard:** `test/privacy/no_content_logging_test.dart` fails if Dart code prints or logs, or if a Kotlin log call interpolates anything besides an exception type. It is a heuristic.

### Current limitation
The queue is drained only while the Flutter side is running. Notifications that arrive while the app is closed wait in the queue (at most 1000 events) until the app is opened. Ingestion with a headless Flutter engine is on the [roadmap](../ROADMAP.md).

## Source navigation (design; implemented in M2)
`SourceRef` stores the notification key, package name and whether a content action existed. A `PendingIntent` is never serialized. Opening the source tries, in order: the live content action while it is still usable; a supported launch intent for the source app; a clear "unavailable" state with the saved content preserved. The manifest declares a `<queries>` entry for launcher apps so labels and launch intents can be resolved without the broad `QUERY_ALL_PACKAGES` permission.

## Database
| Table | Purpose |
|---|---|
| `notifications` | captured notifications, primary key = notification key, index on (package, content hash) |
| `source_rules` | package names for the allowlist/blocklist |
| `app_settings` | key/value settings: filter mode, ongoing and group-summary toggles, retention days |

Generated Drift code (`*.g.dart`) is not committed; `build_runner` creates it locally and in CI.

## Testing
- Domain: plain unit tests with a fixed clock.
- Data: repositories run against in-memory SQLite.
- Capture: the ingestor is tested with a fake `CapturePlatform` and in-memory SQLite; capture events and the status controller have their own tests.
- UI: widget tests drive the inbox, details, import dialog, settings, export, delete and filter screens with in-memory repositories, a fake platform and a fake exporter (no database, no device).
- Not covered by automated tests: the Kotlin code (listener, queue, channels, share receiver, file picker export) and the manifest wiring. They are compiled by the Android build in CI and must be verified on a device, including OEM battery restrictions, restart behavior and lock-screen redaction.
